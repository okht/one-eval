Formal receipt renewal preserves earlier admission records. It cannot change an existing run's mode, runtime or declared deployment bindings. Receipts are valid for 24 hours at operation entry; ongoing batches are not interrupted merely because that period elapses. Reports describe admission when work started and remain readable after expiration.

## Reuse and defects fixed

The connection templates use the existing pinned Promptfoo 0.123.1 providers. The HTTP template uses its object request transform to preserve strings containing JSON-like text, quotes, Unicode and newlines. A regression reproduced an upstream string-body warning that included Authorization headers; the generated configuration now avoids that warning and verifies credential absence in its captured diagnostics. See [Promptfoo HTTP providers](https://www.promptfoo.dev/docs/providers/http/) and [OpenAI-compatible providers](https://www.promptfoo.dev/docs/providers/openai/). Compatibility was checked against the installed pinned implementation, not inferred solely from current documentation.

Packaging uses native npm pack/install and standard official GitHub Actions setup actions. No second evaluation framework or custom package installer was added. Existing proper-lockfile and Zod continue to provide locking and protocol validation. Third-party notices describe the actual dependency roles; the MCP server is a repository benchmark fixture, not a new CLI MCP endpoint.

Independent review also reproduced and fixed three admission boundaries: rejected grading created an orphan version directory and broke report selection; a missing grading manifest could reclassify retained exploratory records; and recovery could run against changed environment bindings. New regressions preserve report readability and prevent those calls. The before/after evidence is retained under results/admission-20261002.

## Remaining limits

The current evidence supports a technical-user internal beta. Broader release still needs real external-service adapter acceptance, human-reviewed business grading anchors and cross-vendor judge validation. The four-platform CI matrix must actually run before claiming those combinations are supported by test evidence.

Adapters and grading scripts remain trusted code without an OS sandbox. Provider statelessness is a declared service contract; hidden remote memory and business state require real managed lifecycle checks. Runtime receipts are local integrity records without signatures. Remote deployment versions, undeclared environment defaults, transitive imports and all transitive installed dependencies are not fully fingerprinted. Formal admission cannot establish general grading accuracy or all-case isolation from a bounded probe.

Larger workloads, stronger process isolation and statistical comparison decisions remain separate work. Current comparisons are descriptive; repeated grades from related models do not establish independent human agreement. These capabilities should continue to use established upstream implementations where their contracts fit.
